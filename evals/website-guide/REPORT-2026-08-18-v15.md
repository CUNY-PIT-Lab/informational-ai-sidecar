## Prompt architecture and provenance

Prompt policy `2026-08-17-v15`, behavior release
`meeting4-contextual-follow-ups`, is the current registered policy. The
repository preserves reconstructed v1, v1-short, v2, v3, v5, v8, v9, and v10
artifacts plus authored v11 through v15 artifacts. The manifest binds each
version to an artifact hash; `prompts/current.md` is the compiled v15 prompt and
the server exposes the same policy ID in health and response metadata.

V15 keeps v14's plain, participant-respectful style and resolves a narrow
follow-up contradiction: the guide should normally advance rather than repeat,
but it should directly confirm, restate, or explain a supported detail when the
participant explicitly asks for that detail. This does not license unsolicited
repetition and adds no program fact to the prompt.

The modular boundary is deliberate:

- Code-owned: automated/non-staff identity, approved source access, one-record
  grounding, no guessing, privacy, sensitive handoff, language controls,
  response validation, rate limits, and deployment gates.
- Reviewable in Prompt Lab: style, clarification phrasing, page awareness, and
  follow-up behavior.
- Runtime data, never settings: the participant's question, current page,
  bounded prior context, retrieved source records, and source excerpts.

This makes the model's contract smaller without making it rigid: retrieve the
best approved evidence, answer naturally and briefly, and abstain when that
evidence cannot support an answer.

- The fixed identity now describes the guide as automated and not a Fortune
  staff member.
- The style module calls for plain, respectful, nonjudgmental language; it
  starts with the useful answer or action and avoids jargon, blame, and
  assumptions about participants.
- Server-side privacy detection now matches the browser for bounded disclosures
  such as a participant's name, address, phone, email, health, or diagnosis.
- The document's request for a human route is satisfied by the existing
  code-owned staff handoff rather than a model promise.

### Retained elsewhere or not adopted

- A blanket statement that active conversations are logged was not adopted.
  Logging is deployment-dependent: approved synthetic staging uses transcript
  capture, while public production must remain capture `none`.
- Specific crisis resources and onsite directions were not adopted without a
  complete Fortune-approved protocol and destination record.
- A global step-by-step tutoring mode was not added to a service-navigation
  product without approved teaching content and a separate evaluation.
- Broad multilingual or multilingual-staff promises were not added without
  approved capability data.
- Cross-site general knowledge was not added; answer authority remains the
  reviewed Digital Equity corpus.
- Program names, schedules, contacts, availability, and eligibility were not
  embedded in the prompt. These facts remain in source records so a source
  change can change the generated answer.
- Source freshness remains visible in health/evaluation provenance. Repeating a
  date in every answer was not adopted; an always-visible freshness label is a
  separate interface decision.

## No-canned and no-guessing evidence

The runtime distinction is between **factual answers** and **server-owned
boundaries**. Privacy/safety copy, a genuine clarification, an error, or “I
couldn't confirm that” is intentionally deterministic; a claim about a class,
service, schedule, device, eligibility rule, contact route, or current status is
not.

Evidence in the final v15 staging artifacts:

- Scattershot: all 33/33 factual `answer` responses report
  `model_called=true`.
- Multi-turn: all 45/45 factual `answer` responses report
  `model_called=true`.
- Every cited answer source in both artifacts uses the approved
  `https://www.fortunedigitalequity.org/` host.
- Both suites are complete and green. The scattershot suite passes
  adversarial/no-guessing, stale-fact-negative, privacy/sensitive-handoff,
  current-status, and concision slices in full.
- The server rejects unknown source IDs, unsupported links, invented
  numbers/units/entities/absolutes, and prose without sufficient overlap with
  the selected record.
- A mutation regression replaces the Intro to Email source with a new fact and
  proves the retrieval prompt and accepted answer change with that record.
  Separate regressions accept multiple natural phrasings grounded in the same
  source, demonstrating that the system is not matching one memorized answer.
- If no approved record supplies evidence or the model is unavailable, the
  runtime does not extract a factual fallback; it routes to staff.

These checks establish the mechanism, not eternal correctness. Every source
refresh must rerun the same mutation, grounding, adversarial, and live-model
evaluation gates.

### Bounded grader-v3 correction

The initial v15 multi-turn response to “So are Fortune's free phones available
now?” was a direct answer to an explicit confirmation question. It called the
model, selected the approved Devices record, said distribution is currently on
hold, and preserved the required stale-positive exclusion. Grader v2 still
failed the turn because its generic advancement check treated any repeated
evidence as a conversational regression.

Contract v3 corrects only that mismatch. It permits
`advancement_required=false` for two named confirmation turns: the previously
documented full-attendance confirmation and this phone-availability
confirmation. The latter is the only new delta from v2 on the initial v15 raw
run. The frozen 12 episodes, 50 participant turns, model response, source
requirement, `model_called=true` requirement, on-hold wording requirement,
stale-positive exclusion, grounding gate, and hard gates are unchanged. Tests
verify that there are exactly two exceptions. This is a grader correction, not
a retroactive runtime fix or a waiver for generic repetition.

The overlay and its explicit lineage are in
[`multiturn-spec-2026-08-17-v3.json`](multiturn-spec-2026-08-17-v3.json). The

### Structured model-output correction

The model contract requires exactly two fields: an approved source `pick` and
an `answer`. The first v15 run included one avoidable page-aware Devices
clarification and finished 40/41. At that point, the Ollama request still used
generic JSON mode, which requested JSON but did not enforce the required shape.
Raw provider text is intentionally not stored, so the result artifact proves
the clarification, not a specific malformed payload; the correction addresses
the structural weakness at the provider boundary.

Commit `43be87f` sends a JSON Schema with required string fields `pick` and
`answer` and `additionalProperties=false`. The server's existing source,
grounding, unsupported-fact, and retry validators remain in force after schema
validation. This tightens transport structure without hardcoding an answer or
expanding factual authority. Contract tests assert the exact schema passed to
the model provider. The fresh exact-commit rerun restored the page-aware case
and passed 41/41.
